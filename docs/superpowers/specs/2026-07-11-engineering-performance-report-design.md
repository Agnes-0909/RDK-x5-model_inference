# 工程技术与性能报告设计

## 目标与读者

在 `mipi_vse_bpu_zerocopy` 工程根目录生成一份面向研发人员的单文件 Markdown 报告 `TECHNICAL_PERFORMANCE_REPORT.md`。报告需要让未参与实现的工程师理解 MIPI、ISP、VSE、零拷贝注册、双 worker、单 BPU core 推理和后处理的完整链路，并能复核当前 X5 实测性能。

## 报告结构

1. 项目目标、硬件及软件环境。
2. 完整数据链路和线程/资源所有权。
3. 零拷贝成立条件、地址证据及静态策略门禁。
4. 日志埋点和各耗时指标的精确定义。
5. 100 帧/路验收方法、原始日志位置和统计方法。
6. 左右路 BPU、后处理、端到端耗时的均值、最小值、P50、P90、P95、P99、最大值。
7. 双路总体吞吐、配对帧率、缓存命中率、地址一致性和错误统计。
8. 2 帧 debug 日志中的后处理阶段构成，仅作为机制解释，不外推为稳定分布。
9. 瓶颈判断、并发行为分析、已知限制和按收益排序的优化建议。
10. 构建、运行、日志提取与性能复现命令。

## 数据来源与口径

- 主性能数据使用板端 `/root/mipi_vse_bpu_zerocopy/logs/run_20260711_221831`，左右各 100 帧、`LOG_LEVEL=info`。
- 后处理分段使用 `/root/mipi_vse_bpu_zerocopy/logs/run_20260711_221544`，左右各 2 帧、`LOG_LEVEL=debug`。
- 从 `events.jsonl` 读取 `dnn.inference_complete` 和 `worker.frame_processed`，从 `summary.json` 读取队列累计等待、缓存和最终计数。
- 分位数采用线性插值，报告中注明算法，避免不同工具默认算法造成歧义。
- 总体吞吐按第一个 `worker.frame_processed` 到最后一个同类事件的单调时钟区间计算；配对帧率为较小的左右完成帧数除以该区间。
- `end_to_end_ms` 的起点是 worker 开始处理已出队帧，不包含 MIPI 曝光、ISP/VSE 硬件处理、主线程取帧和排队等待；报告必须明确这一边界。
- `bpu_ms` 包含 submit、wait、输出 cache invalidate 和 task release；`postprocess_ms` 包含分类扫描、DFL、坐标映射和 NMS。

## 证据与结论边界

- 只把日志能直接证明的内容写成实测结论。
- 200 次 `vse_phy == dnn_phy`、每路三个注册缓存项和静态 API 扫描共同作为零拷贝证据，但不宣称整个平台不存在任何 SDK 内部复制。
- 单次 100 帧测试用于当前版本基线，不等同于温度、电源模式和长时间运行下的完整性能认证。
- 单 BPU core 下的双线程用于生命周期隔离、背压和 CPU/BPU 阶段重叠，不宣称 BPU 算力翻倍。

## 验收标准

- 报告中的全部数值可由指定日志重新计算。
- 左右路及总体指标不混用，耗时边界无歧义。
- 明确区分测量事实、工程推断和优化建议。
- 文件位于工程根目录，Markdown 表格和命令可直接阅读、复制。
- 不修改程序行为，不重新运行板端测试。
